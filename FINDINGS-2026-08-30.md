Defects and friction found by running `persona-brainstorm` against its own repository, end to end:

Companion documents: `PERSONAS.2026-08-30.md` (the run), `PERSONAS.2026-08-30-adversarial.md` (the
adversarial pass). The 2026-08-28 run at `PERSONAS.md` is untouched, as is

**All of these are now fixed on branch `fix/dogfood-2026-08-30`.** Each fix carries a fixture that

## D1 — The `About` block fails a correct document

**Fixed.** `blocks` now holds each block's full extent alongside `labels`' single line, and About is read from it. Two causes, not one: the value was line-scoped, *and* any bold run at line start was parsed as a new label, so `**verified**` after a wrap silently truncated the block above it. Labels are now matched against the closed set of five. Fixtures: `adversarial-about-block-may-soft-wrap`.

**Severity: high — this is the only defect that rejects valid input.**
**Status: confirmed by probe.**

`verify.py:1543` stores each adversarial block's value as `m.group(2).strip()`, the remainder of the
label's own **physical line**. Two other checks in the same loop read different extents: the
empty-block check reads the full block (`:1555`), the evidence mark reads to the next blank line
(`:1577`). One entry, three parsing extents.

**Probe.** Take a passing `About` block and move one line break one word earlier, so the status word
`**verified**` falls on the second physical line. Nothing else changes — same words, same lane, same
status, valid markdown, identical rendering.

```
[FAIL] 1 grievance(s) name no verification status for the lane they cite: P5-1.
```

Wrapping so the lane letter lands on line 2 produces the parallel failure about naming no Appendix A
lane.

**Why this bites in practice.** These lines are long by construction — a lane name, a verification
status and an evidence mark on one line — and `references/adversarial.md`'s own worked example wraps
its heading across lines 148–149 for exactly that reason. The checker handles wrapping deliberately
everywhere else: heading continuation (`:1479-1483`), primitive entries (`:281-293`), carried
findings (`:917-932`).

**Fix shape.** Read the block value with the same extent the empty-block check already uses — label
line plus everything to the next label — and normalise whitespace before matching.

## D2 — An evidence-mark source cannot contain a closing parenthesis, and the error misdiagnoses

**Fixed.** `MARK_SOURCE` accepts a `)` that is not the mark's own delimiter, and `MARK_ATTEMPT_RE` distinguishes a mark that did not parse from a mark that is absent — both now report separately, at both sites. The grievance site had its own copy of the pattern and has been pointed at `MARK_RE`; that copy is why the first fix did not take. Fixtures: `adversarial-mark-source-may-contain-a-parenthesis`, `adversarial-unparseable-mark-is-not-a-missing-one`.

**Severity: medium — wrong diagnosis, and it steers the fix the wrong way.**
**Status: confirmed by probe; hit three times live during this run.**

`MARK_RE` at `verify.py:81` captures the source with a negated class that stops at the first closing
parenthesis. A `)` anywhere inside ends the capture early, the trailing delimiter no longer matches,
and the mark becomes invisible. The checker then reports:

```
[FAIL] N primitive(s) carry no evidence mark: ...
```

An author who wrote a correct, well-formed, sourced mark is told they omitted one. The natural
response is to add a second mark, which `output-template.md:94-95` calls "an error, not a choice."

**The sharpest form.** The text most likely to trip this is *the checker's own output*, because those
messages contain a parenthesised plural. Sourcing an `observed` mark to what the checker reported is
exactly the auditable provenance the method asks for — so the tool punishes its most rigorous
citation.

**Confirmed three times in this run**, twice inside the single grievance documenting the bug: first
when the source quoted the checker's message, then when it quoted the offending regex, which
contains the character by construction. **The bug cannot be documented inside its own evidence
source.** Only prose paraphrase passes, which forfeits the citation the scheme exists to produce.

**Fix shape.** Balanced-paren or non-greedy capture, plus a distinct message for "a mark was found
but could not be parsed."

## D3 — Appendix A can be deleted from a Full-depth document and `--final` still exits 0

**Fixed**, without the new required header this file first proposed. A graded document with no readable Appendix A lanes now warns, and fails under `--final`. Coverage marks are the trigger rather than a declared depth: a depth-None run has neither marks nor appendix, a graded run has both, so the two are told apart by what the document already carries — no new field to leave stale. Fixture: `final-rejects-graded-document-with-no-appendix`.

**Severity: medium-high — every claim the appendix grounds becomes unanchored.**
**Status: confirmed by probe.**

`PERSONAS.md` truncated at its appendix heading passes `verify.py --final` at exit 0 while still
claiming `**Tally:** 7 ✅ · 26 ◐ · 27 ○` — sixty graded marks with nothing left in the file to ground
one of them.

**Root cause is structural, not a missed branch.** `parse()` reads five canonical header declarations
(`verify.py:330-357`) and **coverage depth is not among them**, so the checker cannot distinguish a
legitimate depth-None run (correctly appendix-less) from a Full run whose inventory was dropped. The
adversarial mode handles this at `:1460-1470` because it *needs* the lanes; the core check never did,
so the gap survives in the two invocations everyone actually runs.

**Fix shape.** A `**Coverage depth:**` canonical header declaration (Full / Light / None) on the same
one-address rule as `**Frequencies:**` and `**Roster axis:**`. Then Full or Light implies Appendix A
must exist and carry lanes; None implies it must not, and the coverage column must be absent. The
same declaration hands the enrichment pass the depth signal it currently infers from whether marks
are present.

## D4 — A Verification section of five one-character lines passes `--final`

**Fixed.** Both sites now count `is_substantive()` lines rather than non-empty ones. Fixture: `final-rejects-five-placeholder-lines`.

**Severity: medium — the gate exists to catch exactly what it admits.**
**Status: confirmed by probe.**

A Verification section whose entire body is `x` / `y` / `z` / `a` / `b` passes at exit 0. The
threshold is a pure non-empty line count and it is exactly five: the same document with a one-line
body fails with *"Verification section has 1 non-empty line(s)."* (`verify.py:1818-1824`,
`:1402-1405`).

So the check fires on an *empty* section and passes on a *meaningless* one. The comment at
`:1815-1817` states the intent — "require enough substance to have carried them" — and a line count
does not deliver it.

**Fix shape.** `is_substantive()` already exists at `verify.py:129-150` and would reject `x`.
Applying it per line raises the bar from five keystrokes to five sentences without pretending to
judge content. It cannot verify a second agent existed — nothing can — but `SKILL.md:675-676`
already permits declaring one was unavailable, so the residue is disclosed rather than hidden.

## D5 — A count stated in prose is invisible to the checker, and that is where this run broke

**Severity: low mechanically, high as a lesson. Not straightforwardly fixable.**
**Status: found by Phase 7b, in this run's own document.**

The core document's appendix claimed *"ten rules ship as WARN"* and enumerated eight, each with a
`file:line`. Phase 7a passed it at zero warnings — correctly. `verify.py` reads claimed figures only
from the canonical tally line (`:319-329`), and `SKILL.md:653-656` explains why: a good document
discusses numbers in prose, and a checker scanning everywhere would read that discussion as a claim.

**The irony is the finding.** That document cites a prior run self-reporting "⚡ count: 21" for a
document carrying 26 as the strongest evidence on the page for why `self-assessment` is needed — and
then reproduced the same failure, two paragraphs from the citation, unnoticed.

**Do not "fix" this carelessly.** Widening the checker to scan prose would break the one-address
discipline that keeps it honest. Realistic mitigations are narrower: flag a prose cardinal
immediately followed by an enumeration of disagreeing length, or state in `SKILL.md` that this class
of error belongs to Phase 7b — which at least tells an operator what the checker is not covering.

## D6 — A markdown italic closing a sentence defeats the scene-disclosure check

**Fixed.** The sentence split now steps over trailing markdown and quote characters, so an italic-closed provenance line ends a sentence. Verified by restoring the wording the enrichment pass had to work around.

**Severity: medium — reports a correct, present declaration as absent.**
**Status: confirmed by probe; hit live during the enrichment pass.**

`verify.py:1303` splits the enriched header into sentences with `re.split(r"(?<=[.!?])\s+", header)`.
A sentence that ends with an italic close — `…changes nothing in it._` — has `_` immediately before
the whitespace, not `.`, so **the lookbehind never fires and no split occurs**. The provenance line
and the scene disclosure then land in one chunk, and `affirms()` at `:1293-1301` rejects it, because
its negation guard scans everything preceding `are invented` and finds the unrelated `nothing`.

**Probe.** Two headers differing only in the final word of the provenance line:

| Header ends | `affirms()` |
|---|---|
| `…changes nothing in it._` | **False** — declaration reported absent |
| `…leaves it untouched._` | True |

The declaration is present, correct and identically worded in both.

**Why this is reachable.** Italic-terminated sentences are the templates' own house style —
`output-template.md` and `references/adversarial.md` both open with `_…._` provenance lines, and
`enrichment.md` specifies one. Any negation word anywhere in that line (`nothing`, `not`, `no`,
`never`, `none`) collides with the disclosure that follows it.

The reported failure — *"the enriched header carries no affirmative statement that the scenes are
invented"* — names the wrong cause, exactly as D2 does. The author's fix is to reword a sentence
that was never wrong.

**Fix shape.** Split on `(?<=[.!?])[_*"'”’)\]]*\s+` so trailing markdown and quote characters do not
suppress the boundary, or scan for the disclosure clause directly rather than sentence-wise.

## D7 — The frequency vocabulary has two homes and they disagree

**Fixed** in the direction of the checker: `monthly` and `annually` are now published in `SKILL.md`, which also records that the two lists must change together, and notes that `onboarding` is a lifecycle stage rather than a cadence.

**Severity: low. Status: confirmed by grep.**

`verify.py:23` accepts `monthly` and `annually`. `SKILL.md:391` publishes eight values and neither is
among them. `grep -rn 'monthly\|annually' skills/ README.md` returns exactly one hit — the checker
itself.

Low impact, since an out-of-vocabulary frequency is a WARN either way. Recorded because it is the
drift shape this repository's history keeps closing.

**Related, and larger:** Phase 7b observed that the column is not a frequency column at all —
`onboarding` is a lifecycle stage, not a cadence, and sits beside `many/day`. That is a design
question about the published vocabulary, not a code defect.

## F1 — `cross-run.md` is unreachable in time from Phase 0

**Fixed.** Phase 0 step 3 now says to check for a prior document and read `references/cross-run.md` before asking for the budget.

**Severity: medium. This is an ordering bug in the instructions.**

Phase 0 asks for the item budget at step 3. `references/cross-run.md:56-62` — which requires subject,

An operator who asks the seven questions in the order written, lets the user pick a bigger budget
because doubling sounds like reaching further, and reads `cross-run.md` afterwards has already

**Fix shape.** One sentence in Phase 0 step 3: if a prior document exists for this subject, read
`references/cross-run.md` before asking, and offer the comparison re-run explicitly.

## F4 — The re-run path for this repository's own document is undefined

**Not fixed — left for you.** Adopting a new `PERSONAS.md` needs the seed regenerated from it, and defining that sequence by doing it is your call, not mine.

**Severity: medium as a process gap. Not a bug.**

`tests/run_fixtures.py:1237-1244` asserts bidirectional equality between the primitive slugs in
`PERSONAS.md` and the seed table in `references/primitives.md`. The pin is deliberate and correct:
the seed is read-only and describes exactly one run, and each direction catches a real mistake, as
the comment there explains.

What is undefined is what happens when that run is superseded. A healthy re-run reuses some slugs and
mints others — `cross-run.md` says so explicitly, and says a primitive appearing in one pass and not
the other is a weak primitive whose absence should be reported rather than quietly kept. Adopting
such a re-run as `PERSONAS.md` fails both assertions until the seed is regenerated from it, and
nothing documents that regeneration as a step.

This run therefore wrote to a dated path, which `cross-run.md:42-48` sanctions.

**Fix shape.** Document the adoption sequence: snapshot the old document, replace `PERSONAS.md`,
regenerate `references/primitives.md` from the new synthesis, re-run the suite.

**The dead ternary at `verify.py:1126-1127`** is redundant, not wrong. Both branches yield `"unlike"`
— and both branches *are* "unlike", because the guard above fires only on disagreement and the footer
disagrees with the core in either direction. Worth deleting on sight; not worth filing.

**The `Kind` field's strictness.** Five of eleven grievances in the adversarial pass failed because a
clause was appended to the value (`it refuses — quietly, by declining to enforce`).
`references/adversarial.md` says "one of the five"; the checker means verbatim. That is correct
enforcement with an error message that names the closed set. Recorded only because the surrounding
prose invites elaboration the field forbids.

**Persona distinctness being unchecked** is a deliberate decision with a measured rationale, not an
oversight: a lexical version scored true duplicates *lowest*, 0.031 against 0.123 for unrelated
pairs (`verify.py:763-772`). The right call.
